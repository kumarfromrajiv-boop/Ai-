Anonymous requests are associated with an HTTP-only, secure, same-site browser cookie. IDs alone do not grant access; clearing cookies loses browser access to prior tasks. Records survive closing the tab. A database partial unique index allows only one globally queued/running job. Blocked requests do not occupy that slot. A background function atomically consumes a one-use dispatch nonce and runs independently of the browser, up to the platform's 15-minute maximum. Jobs older than 16 minutes are marked unconfirmed/failed when status is read or a new task is submitted. This is bounded background execution, not an indefinitely running automation engine. The system does not automatically replay uncertain side effects after failure.

No build or local execution validation was run during creation. The deployment pipeline installs dependencies, validates the project, and applies migrations.

## Task conversation and cancellation

The third screen now shows the original URL/instruction and follow-up user messages on the right, with AICredits-generated replies on the left. Conversations persist in `job_messages` and inherit the job's cookie-based ownership checks. When the screen observes a changed task snapshot, it requests an AI explanation once for that snapshot; a deterministic message ID prevents duplicate AI requests across reloads and instances. Replies use the configured AICredits model after catalog validation, without silently switching providers or models. Provider failures appear as connection notices, not fabricated AI replies. The assistant receives the saved status, plan and result; it cannot observe additional browser activity. Follow-up chat asks questions about the task; it does not change an in-flight execution plan. Automated explanations are requested while the screen is open and on return.

Cancellation is owner-only and idempotent. Queued or blocked jobs are cancelled without dispatch. Running jobs retain their active database slot while cancellation remains unconfirmed. The executor checks the persisted cancellation request before every browser call and before recovery. A completion arriving before cancellation confirmation remains a completion, because the work actually finished.

Workers should implement authenticated `POST /cancel` with `{ "jobId": "..." }`. Return `{ "status": "cancelled" }` only after all execution for that ID has stopped. The worker must durably record a cancellation tombstone and reject any concurrent or later `/execute` for the same job, including a request racing with cancellation. Repeated cancellation requests must be safe. A missing endpoint, error or any other response leaves cancellation unconfirmed; it must never be interpreted as a successful stop. Cancellation does not undo prior side effects. Jobs still use the existing timeout and never automatically replay uncertain actions.
